# 新增分组

POST `/api/short-link/admin/v1/group`，Headers 传 `username`、`token`，JSON 请求体为 `{"name":"学习资料"}`。
复用现有登录中间件和 Result；成功 data 为 null，业务失败仍返回 HTTP 200，通过 code/success 判断。

## 创建流程

1. 从可信上下文获取用户名，验证名称去除首尾空白后为 1～64 个字符。
2. 获取该用户 Redis 分组创建锁，竞争失败返回 A000300。
3. 统计对应分表内 del_flag=0 的分组，达到 20 个返回 A000501。
4. 最多尝试 10 次生成 6 位字母数字 gid；布隆过滤器预判后尝试唯一表登记。
5. 在同一 MySQL 事务内完成唯一表登记和分组插入；失败回滚。
6. 提交后加入过滤器；同步失败记录日志，接口仍返回已创建成功。

## 与 Java 原版的对应和边界

- 沿用用户级 Redis 锁、随机 gid、布隆过滤器、唯一表、数量上限和重试流程。
- 使用 RedisBloom BF 命令，不兼容 Redisson 过滤器内部存储格式。
- 原版无显式事务注解；Go 版本让两张 MySQL 表的写入共用事务。
- 固定锁租期 30 秒，业务上下文 5 秒；不实现 Redisson 自动续期。长时间进程暂停等导致租期失效时，数量上限不能获得严格并发保证。
- 最终 gid 唯一性由数据库唯一索引保障；MySQL 与 Redis 不具有共同事务。
- 过滤器提交后同步失败由日志暴露，下次启动从 t_group_unique 补入；当前没有持续运行中的自动补偿任务。
- 过滤器启动导入仅适用于当前本地单实例启动模式。
- 名称允许重复，分组创建接口不接收客户端指定的所属用户名。

## 启动前准备

在本地 MySQL 执行 resources/database/group.sql，确认 t_group_0～15 和 t_group_unique 存在。
脚本不由程序自动执行；不要通过删表重跑脚本清理学习数据。
Redis 使用现有 Docker 实例 127.0.0.1:6379，须支持 BF.RESERVE/BF.ADD/BF.EXISTS。
启动时先 Prepare，再从唯一表导入全部 gid，最后 MarkReady，完成后才监听请求。

## Apifox 验证

先登录，把返回的 token 和用户名填入 Headers，再发送新增请求。
验证正常创建、缺少登录、无效 token、空名称、纯空格名称、超长名称、重复名称以及达到 20 个有效分组后的拒绝。
检查分组分表记录与唯一表登记对应；test3 按现有规则位于 t_group_1。

自动化测试不使用真实 MySQL/Redis，也不会创建测试账号或分组。
事务驱动测试覆盖提交、回滚、开启失败和提交失败的错误传播；路由测试覆盖登录拦截和参数错误。
真实 Redis 锁竞争、BF 命令和 MySQL 唯一索引行为仍需在本地依赖启动后进行集成验证。
